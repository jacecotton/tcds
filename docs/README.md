This directory contains the Design System's documentation site.

## Architecture
### Technical architecture
#### Environment
Using a Markdown-based SSG workflow. Generated directly from the Design System codebase itself to reduce documentation overhead, prevent drift, facilitate faster iteration and testing in development, and to test the design system's interoperability with other environments than Drupal.

* **Node.js** — quick environment setup, non-Drupal/Symfony/PHP stack for interoperability stress-testing/dependency monitoring
* **Eleventy** — markdown-based SSG pages, directory-based routing, Twig-compatible templating
* **Twing** — explicitly models itself more closely on PHP Twig as compared to Twig.js
  * **`@christianwiedemann/drupal-twig-extensions`** — ports Drupal and Symfony-specific features to Twing
  * **`drupal-attribute`** — emulates Drupal's `Attribute` object in JavaScript

#### Data pipeline
The Design System exposes structured information in four domains that Eleventy can consume and render dynamically, keeping the documentation and the codebase in sync.

1. **Tokens** — live design values derived from the Design System's JSON token files, piped through its Style Dictionary config (see `docs/_data/tokens.js`)
1. **Public custom properties** — component-specific design values are not stored as tokens, but instead as custom properties within the component's stylesheet itself; annotated with `@public`, manifest generated by a PostCSS plugin
    1. *Future consideration*: harvest additional metadata from `@property` declarations when and where used
1. **Custom element APIs** — a manifest file for component element APIs (attributes, methods, events, shadow parts, etc.) is automatically generated via `@custom-elements-manifest/analyzer`
1. **Component template contracts** — component template contracts (props, slots, component meta, etc.) are authored in `.component.yml` files (per [SDC architecture](https://www.drupal.org/docs/develop/theming-drupal/using-single-directory-components))

```
tsc --allowJs --checkJs --noEmit
cem analyze
```

#### Testing
`docs/` is first on the E2E/integration testing front. Needs to prove whether the Design System can be successfully consumed by a completely separate environment from the primary Drupal target.

Stack:
* **Playwright** — runs the actual application and interacts with a real browser

For CI:
* **`docs:build`** — Eleventy build itself is a test (catch sneaky Drupal assumptions in Twig, etc.)
* **`docs:test`** — for each component, tests page rendering, route correctness, and component presence (not behavior)

### Information architecture
* Introduction — what's available, how to set it up
* Foundation — color, layout, typography, etc.
* Components — usage guidelines, features, behavior specs, API documentation
* Patterns — combination recommendations and usage guidelines
